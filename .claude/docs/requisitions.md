## ช่องว่างที่หน้านี้มีไว้ปิด

**ตอนนี้ไม่มีสะพานระหว่าง “ผู้สมัคร” กับ “ติดตามฝึกงาน” เลย** — `getTraineeBoard()` อ่าน
`hr_service.master_driver` อย่างเดียว ส่วนใบสมัครใน `recruitment_regist_answer` ไม่มี
`drivercode` สักตัว → ผู้สมัครที่ `status = "training"` **ไม่มีทางโผล่บนตารางฝึกงาน**
จนกว่า ETL จะสร้างเขาใน `master_driver` · นี่คือเหตุผลที่โมเดลข้างล่างมี `drivercode`
อยู่บนคำขอ ไม่ใช่ฟิลด์เกินมา

## โมเดลข้อมูล — `hr_service.recruitment_requests`

แพตเทิร์นลอกจาก `lib/record-cases.ts` ทั้งชุด: เอกสารเดียวจบ (รวมประวัติ) ·
`ensureIndexes` ครั้งเดียวต่อโปรเซสและ**ล้มเหลวแล้วไม่โยนต่อ** · `LIST_LIMIT = 500` ·
ตัวนับเลขที่รายเดือนอยู่คนละคอลเลกชัน

```ts
/** 1 เอกสาร = 1 อัตรา */
interface RequisitionDoc {
  code: string;              // "RQ2609-001"  RQ + yymm + running 3 หลัก
  requestedOn: string;       // "YYYY-MM-DD" วันที่แจ้งสรรหา

  position: "ML" | "MS" | "spare" | "other";
  positionOther: string;
  customer: string;          // จาก CUSTOMERS หรือ "other"
  customerOther: string;
  plant: string;

  hireType: "replace" | "new_rate";
  /** null เมื่อ new_rate — ต้อง **ล้างค่าจริง** ไม่ใช่แค่ซ่อนบนจอ */
  replace: {
    drivercode: string;      // อ้าง master_driver.drivercode
    name: string;            // สำเนาชื่อ ณ วันที่แจ้ง (ชื่อในทะเบียนเปลี่ยนได้)
    reason: string;          // รหัส Reason Code Master เช่น "P4" (ใบเก่า: "resigned" ฯลฯ → LEGACY_REPLACE_REASON_LABELS)
    reasonLabel: string;     // สำเนาป้าย ณ ตอนบันทึก
    reasonNote: string;      // รายละเอียดเพิ่มเติม (ไม่บังคับ)
  } | null;

  /** สำเนาจาก Boom_ETL.vehicles — เก็บสำเนาเพราะรถถูกย้าย/ปลดได้ */
  vehicle: { code: string; plateNo: string; brand: string } | null;

  /** 👑 ครูฝึก — แหล่งความจริงที่เดียวของทั้งระบบ ห้ามก๊อปไปไว้ที่อื่น */
  trainer: { drivercode: string; name: string } | null;

  status: "open" | "matched" | "filled" | "cancelled";
  cancelReason: string;
  filledOn: string;

  /** 🔗 ใบสมัครที่รับอัตรานี้ — null = ยังไม่มีใคร */
  match: {
    applicationId: string;   // hex ของ _id ใน recruitment_regist_answer
    ref: string;             // "DRV-69-0031" — โชว์ได้โดยไม่ต้อง join
    fullName: string;
    linkedAt: string;
    linkedBy: string;
  } | null;

  /** 🔗 สะพานไปหน้าฝึกงาน — ว่าง = ยังไม่ขึ้นทะเบียน พจส. */
  drivercode: string;

  note: string;
  requester: { employeeId: string; name: string };   // จาก session เท่านั้น
  history: { at: string; by: string; from: string; to: string; note: string }[];
  createdAt: string;
  updatedAt: string;
}
```

**ดัชนี**

```
{ code: 1 }                    unique
{ status: 1, requestedOn: -1 }                                  // ตารางหลัก
{ drivercode: 1 }              partial: drivercode ≠ ""         // join หน้าฝึกงาน
{ "match.applicationId": 1 }   unique partial: match ≠ null && status ≠ "cancelled"
```

**ตัวนับ** `recruitment_counters` — เอกสารเดียวต่อเดือน (`{_id:"requisitions:2609", seq:12}`)
`findOneAndUpdate` + `$inc` + `upsert` ตาม `record_counters` เป๊ะ

## สถานะคำขอ — 4 ตัว ที่**ไม่ซ้ำกับ `APPLICATION_STATUSES`**

หลักคิด: **คำขอตอบว่า “อัตรานี้ยังต้องหาคนอยู่ไหม” · ใบสมัครตอบว่า “คนคนนี้เดินถึงไหนแล้ว”**
ใส่ “กำลังสัมภาษณ์” ลงในสถานะคำขอเมื่อไหร่ คือการก๊อป `interview_scheduled` ไว้สองที่
แล้วจะมีวันที่สองที่ไม่ตรงกันโดยไม่มีใครรู้ — **อย่าเพิ่ม**

```ts
REQUISITION_STATUSES = ["open", "matched", "filled", "cancelled"]
// เปิดรับ · ได้ผู้สมัครแล้ว · เริ่มฝึกงานแล้ว · ยกเลิกคำขอ
```

⚠️ `filled` เปลี่ยนป้ายจาก "ได้คนแล้ว" เป็น **"เริ่มฝึกงานแล้ว"** (22 ก.ย. 2026) —
คลุมเครือกับ `matched` เกินไป (แค่ผูกใบสมัคร ยังไม่เริ่มฝึกจริง) ป้ายใหม่บอกตรงว่า
ทรานซิชันนี้เกิดตอนไหน (`matched → filled` เมื่อใบสมัครที่ผูกไว้เข้าสถานะ `training`)

| จาก → ไป | ใครสั่ง | เมื่อไหร่ |
|---|---|---|
| — → `open` | ระบบ | สร้างคำขอ |
| `open` → `matched` | ระบบ | ผูกใบสมัครสำเร็จ |
| `matched` → `filled` | ระบบ | ใบสมัครที่ผูกไว้เปลี่ยนเป็น `training` → ตั้ง `filledOn` |
| `matched` → `open` | ระบบ | ใบสมัครที่ผูกไว้กลายเป็น `cancelled` → **ปลดการผูกและเปิดอัตราใหม่** |
| ใด ๆ → `cancelled` | **คนเท่านั้น** | กดยกเลิก + เลือกเหตุผล ผ่าน `confirm({ tone: "danger" })` |
| `cancelled` → `open` | คน | “เปิดรับอีกครั้ง” |

⚠️ ทรานซิชัน `matched → open` สำคัญมาก — ไม่มีตัวนี้ อัตราที่ผู้สมัครถอนตัวจะค้างเป็น
`matched` ตลอดกาลโดยไม่มีใครเห็น

**ปิดคำขอได้ 2 ทางเท่านั้น** — `filled` (ระบบปิดให้เมื่อผู้สมัครเริ่มฝึก) และ `cancelled`
(คนกดพร้อมเหตุผล) · **ไม่มีปุ่มลบ** เพราะ “เดือนนี้ยกเลิกไปกี่อัตรา เพราะอะไร” ต้องรวมยอดได้
(หลักเดียวกับ `EXIT_REASONS` ที่แยกเหตุผลออกจากสถานะ)

## 1 คำขอ = 1 อัตรา = ผู้สมัครไม่เกิน 1 คน

```
คำขอ RQ2609-001 ──(match)──► ใบสมัคร DRV-69-0031 ──(drivercode)──► แถวในตารางฝึกงาน
   1 อัตรา                      0 หรือ 1 ใบ                        0 หรือ 1 แถว
```

ทุกฟิลด์ปลายน้ำของคำขอเป็นของรายบุคคล — รถคันเดียว คนที่ถูกแทนคนเดียว ครูฝึกคนเดียว ·
ผูกหลายคนเข้าใบเดียวเมื่อไหร่ ฟิลด์พวกนี้กำกวมทันที · **การสัมภาษณ์หลายคนเพื่ออัตราเดียว
เป็นงานของโมดูลผู้สมัคร ไม่ใช่ของคำขอ**

**กติกาที่เซิร์ฟเวอร์ต้องบังคับ** (ไม่ใช่แค่ซ่อนปุ่ม):
- ผูกได้**ทุกสถานะยกเว้น `cancelled`** (`LINKABLE_STATUSES`) — 🔀 เปลี่ยนตามคำสั่งเจ้าของงาน
  29 ก.ย. 2026 เดิมเฉพาะ `interview_passed` / `training` · ตอนนี้ฝ่ายบุคคลเลือก RQ ให้ผู้สมัคร
  ได้ตั้งแต่ขั้นแรกจากกล่อง “ทำเอกสาร” (`hr-document-maker.tsx` ช่องตำแหน่งที่สมัคร) และคำขอ
  เป็น `matched` ทันที · ผู้สมัครถูกยกเลิกเมื่อไหร่ `syncRequisitionForApplication()` ปลดและ
  เปิดรับใหม่ให้เองเหมือนเดิม · **อย่ากลับไปบังคับแบบเดิมถ้าไม่ได้สั่ง**
- ใบสมัคร 1 ใบผูกกับคำขอที่ยังไม่ยกเลิกได้ **ใบเดียว** (unique partial index)
- ผูกผิดคน → “ปลดการผูก” ลงประวัติ ไม่ลบเงียบ

## สองแท็บใต้หัวเดียว — คำขอ + ผู้สมัคร (22 ก.ย. 2026)

**ทำไม** — คำถามจริงของฝ่ายสรรหาคร่อมสองตารางเสมอ: *อัตรานี้ได้คนหรือยัง* และ
*คนนี้มารับอัตราไหน* · แยกเป็นสองเมนูแปลว่าต้องเด้งไปมาทั้งวันและจำชื่อข้ามหน้าเอง

```
/recruitment/admin/requisitions            → แท็บคำขอสรรหา (ตั้งต้น)
/recruitment/admin/requisitions?tab=candidates      → แท็บผู้สมัคร
/recruitment/admin/requisitions?tab=candidates&ref=AP26-0031   → + กรองที่ใบนั้น
/recruitment/admin/candidates[?ref=]       → redirect() ไปข้างบน (เส้นทางเก่า ห้ามลบ)
```

| ชิ้น | ไฟล์ | หน้าที่ |
|---|---|---|
| เปลือกแท็บ | `_components/admin/recruitment-tabs.tsx` | `"use client"` · ถือ `tab` + **ข้อมูลของทั้งสองตาราง** + `focusRef` |
| แท็บ 1 | `_components/admin/requisitions-view.tsx` | รับ `title` `tabs` `rows` `setRows` `onOpenCandidate` |
| แท็บ 2 | `_components/admin/candidates-view.tsx` | รับ `title` `tabs` `rows` `setRows` `initialTerm` |

**กติกาที่ตัดสินไว้แล้ว — อย่ารื้อโดยไม่ถาม**

- **โหลดข้อมูลทั้งสองแท็บพร้อมกันตั้งแต่เปิดหน้า** (`Promise.all` สี่ตัวใน `page.tsx`:
  คำขอ · ตัวเลือกฟอร์ม · ใบสมัคร · ผู้ติดต่อกลับ) ไม่ใช่โหลดตอนกดแท็บ — สี่ชุดไม่ขึ้น
  แก่กัน ยิงพร้อมกันช้าเท่าตัวที่ช้าที่สุดตัวเดียว ส่วนการโหลดทีหลังจะแลกมาด้วยการรอ
  **ทุกครั้งที่สลับแท็บ** ซึ่งคือสิ่งที่คนใช้หน้านี้ทำบ่อยที่สุดหลังรวมหน้า
- **`rows` ของทั้งสองตารางอยู่ที่เปลือกแท็บ ไม่ใช่ในตาราง** — ตัวเลขงานค้างบนหัวแท็บ
  ต้องขยับตามทันทีที่ยกเลิกคำขอ/เลื่อนสถานะใบสมัคร ถ้าปล่อยให้ตารางถือเอง ตัวเลขจะค้าง
  อยู่กับค่าที่โหลดมาตอนเปิดหน้าและกลายเป็นตัวเลขที่โกหก
- **เรนเดอร์เฉพาะแท็บที่เปิดอยู่** (ท่าเดียวกับ `components/desk/survey-view.tsx`)
  → ตัวกรองของตารางรีเซ็ตเมื่อสลับแท็บ **ยอมรับไว้แล้ว** แลกกับการไม่ต้องแบกสองตาราง
  เต็มใน DOM ตลอดเวลา · ข้อมูลไม่ได้โหลดใหม่ การสลับจึงยังทันทีเสมอ
- **แท็บเขียนกลับ URL ด้วย `window.history.replaceState` ไม่ใช่ `router.push`** —
  หน้าเป็น `force-dynamic` ถ้า `push` จะยิงอ่าน Mongo ใหม่ทั้งชุดเพียงเพราะกดสลับแท็บ
- **ตัวเลขบนหัวแท็บ = งานค้าง ไม่ใช่จำนวนแถวทั้งหมด** · ความหมายเดียวกันทั้งสองแท็บคือ
  “ยังรอให้ทำอยู่”: คำขอ = `status === "open"` · ผู้สมัคร = `status === "pending_contact"`
  (มี `title` + `sr-only` กำกับ ไม่ให้เดาว่าเลขนี้คืออะไร)
- **ปุ่ม “ขอสรรหา” โผล่เฉพาะแท็บคำขอ** — มันสร้างคำขอ ไม่ได้สร้างใบสมัคร (ใบสมัคร
  เข้ามาจากฟอร์มหน้าบ้านเท่านั้น) ปุ่มสร้างที่ค้างอยู่บนตารางที่มันสร้างอะไรไม่ได้
  คือปุ่มที่ต้องหยุดอ่านว่ามันจะสร้างอะไร
- **การ์ดสรุป 4 ใบเป็นของแท็บคำขอ · `CandidateInsights` เป็นของแท็บผู้สมัคร** — ไม่มี
  ทางเห็นพร้อมกัน จึงไม่มีทางอ่านสลับว่าตัวเลขไหนของใคร และหน้าไม่ยาวขึ้นจากการรวม

**สะพานระหว่างสองตาราง — มีเส้นเดียว** กดชื่อในคอลัมน์ “ผู้สมัครที่รับอัตรา” แล้ว
ข้ามไปแท็บผู้สมัครพร้อมกรองที่ใบนั้นไว้ให้ (`onOpenCandidate(match.ref)` → `?ref=`
→ ตัวกรองคอลัมน์ชื่อ ซึ่งผู้ใช้เห็นและล้างทิ้งได้เอง)

⚠️ **ทางกลับ (จากใบสมัคร → คำขอ) ไม่ได้ทำโดยตั้งใจ** — แถวผู้สมัครไม่มีเลขที่คำขอ
อยู่ในตัว (`ApplicationSummary` ไม่มีฟิลด์นั้น) จะทำต้องแก้ชั้นข้อมูลด้วย ซึ่งเกิน
ขอบเขตของงาน “รวมสองหน้า” · ถ้าจะทำจริงต้องเริ่มที่ `listApplications()`

อยู่แล้วในแถวเดียวกัน กันสับสนว่าสีนี้บอกสถานะไปด้วย:

| ประเภทอัตรา | คลาส |
|---|---|
| `replace` (แทนคนเดิม) | `bg-base-200 text-ink` |
| `new_rate` (อัตราใหม่) | `bg-primary/10 text-primary` |

## คอลัมน์ “จัดการ” + ครูฝึก — ไทม์ไลน์สามรอบในวันเดียว (22 ก.ย. 2026)

**รอบ 1 (เช้า):** ตัดช่องแก้ในแถวออกทั้งหมด (ครูฝึก/ผู้สมัคร/สถานะที่เคยแก้ตรง ๆ)
ย้ายไปโมดัลดินสอ (`RequisitionEditModal`) แทน — ตารางที่ทุกช่องแก้ได้คือตารางที่
กดพลาดได้ทุกช่อง

**รอบ 2 (บ่าย):** ถอดไอคอนดินสอออกไปอีกที ตามคำขอเจ้าของงาน — `requisition-edit.tsx`
ถูกลบทิ้ง ครูฝึก/รถ/ผู้สมัครที่ผูก/รหัส พจส. ไม่มีทางแก้จากหน้านี้เลย ทะเบียนรถกับ
ครูฝึกทั้งคู่ถูกย้ายไปสร้างเป็นจุดแก้ใหม่ที่หน้าติดตามฝึกงานแทน (ไอคอนรถ + ดินสอ
ครูฝึกบนแถวพนักงาน)

**รอบ 3 (เย็น):** เจ้าของงานขอ **ครูฝึกกลับมาแก้ที่หน้าขอสรรหาเหมือนเดิม** — ไม่ต้อง
อยู่หน้าติดตามฝึกงาน จุดแก้ครูฝึกที่เพิ่งสร้างในหน้านั้น (รอบ 2) ถูกรื้อถอนทั้งหมด
(ดูหัวข้อ “ครูฝึกไหลไปหน้าฝึกงานยังไง” ข้างบน) แล้วสร้าง `TrainerCell` กลับมาแทนที่
ในตารางคำขอ — **ทะเบียนรถยังอยู่หน้าติดตามฝึกงานเหมือนเดิม ไม่ได้ถูกขอคืนด้วย**

ผลลัพธ์สุดท้าย: **ครูฝึกแก้ในช่องได้ตรง ๆ ที่หน้าขอสรรหา** (ช่องเดียวในทั้งตารางที่
แก้ได้) — รถ/ผู้สมัครที่ผูก/รหัส พจส./หมายเหตุ ยังไม่มีจุดแก้ไขให้เลย ถ้าเจ้าของงาน
ขอกลับมาอีก ให้ถามก่อนว่าจะแก้จากหน้าไหน อย่าเดาเอาเอง — ประวัติสามรอบข้างบนคือ
เหตุผลที่ต้องถามแทนที่จะเดา

| ไอคอน/ช่อง | ทำอะไร | เปิดอะไร |
|---|---|---|
| ✎ ครูฝึก (ทุกแถว รวมคำขอที่ปิดแล้ว) | ตั้ง/เปลี่ยน/ถอดครูฝึก | `TrainerCell` — `Select searchable clearable` แบบเดิมก่อนตารางเปลี่ยนเป็นอ่านอย่างเดียว ยิง `PATCH { trainerDrivercode }` ตรง ๆ ไม่มีโมดัล ไม่ถามยืนยัน (ย้อนกลับได้ด้วยการเลือกใหม่) |
| 🗑 ถังขยะ (แถวที่ยังไม่ยกเลิก) | ยกเลิกคำขอ | `RequisitionCancelModal` — เลือกเหตุผลจาก `CANCEL_REASONS` แล้วกด “ยกเลิกคำขอ” ครั้งเดียว (โมดัลเป็นทั้งกล่องเลือกเหตุผลและกล่องยืนยันในใบเดียว ไม่ถามซ้ำสองรอบ) |
| ↺ เปิดรับอีกครั้ง (แถวที่ยกเลิกแล้ว) | สลับที่ถังขยะ เมื่อ `status === "cancelled"` | ยิง `PATCH { status: "open" }` ตรง ๆ ไม่มีโมดัล — ไม่มีอะไรให้เลือก ย้อนกลับได้ด้วยการยกเลิกใหม่ถ้ากดผิด |

**สถานะ `matched`/`filled` ยังกดเองไม่ได้เหมือนเดิม** — ไม่มีช่องไหนในทั้งหน้าให้เลือก
สถานะตรง ๆ เลย มีแค่ยกเลิก/เปิดรับอีกครั้งเท่านั้นที่เป็นคำสั่งของคน ที่เหลือระบบตั้งเอง
ตามความคืบหน้าของใบสมัคร (ดูตารางทรานซิชันด้านบน)

**สีชิปสถานะคำขอ** — จงใจไม่ให้ซ้ำหน้าตากับ `StatusPill` ของใบสมัครที่อยู่แถวเดียวกัน

| สถานะ | คลาส |
|---|---|
| `open` | `bg-st-new text-st-new-ink` |
| `matched` | `bg-st-wait text-st-wait-ink` |
| `filled` | `bg-st-live text-st-live-ink` — **ไม่ใช้ `bg-primary`** ซึ่งสงวนให้ `training` ของใบสมัคร |
| `cancelled` | `bg-alert/12 text-alert` |

`text-sla` ใช้กับเลข “รอมาแล้ว” เมื่อเกิน 30 วัน (token SLA breach ของทั้งระบบ)

**กฎที่ต้องไม่พลาด** (จาก `.claude/docs/forms.md`):
- **required คือค่าตั้งต้น** — ช่องไม่บังคับต้องใส่ `optional` ไม่งั้นมันประกาศตัวว่าบังคับ
- สลับ `แทนคนเดิม → อัตราใหม่` ต้อง **ล้างค่า `replace_*` จริง** ไม่ใช่แค่ซ่อน ไม่งั้นได้เอกสาร
  ที่เป็นอัตราใหม่แต่มี `replace.name` ติดไปด้วย
- `Select.Root` รับ `value={value}` เท่านั้น ห้าม `value || undefined` · `Select.Content` ต้องมี `z-60`
- ไม่ใส่ `hint` พร่ำเพรื่อ — มีแค่ 2 จุดข้างบนที่อธิบายพฤติกรรมที่ชื่อช่องบอกไม่ได้

**ตัวเลือก dropdown โหลดฝั่ง server ส่งลงมาเป็น props** (ท่าเดียวกับ `contactOptions`
ในหน้าผู้สมัคร) **ไม่ต้องทำ endpoint ค้นหา**:
- พจส.: `master_driver.find({ active: true }, { projection: { drivercode:1, driverName:1, branch:1 } })` ≈ 600 แถว ≈ 40 KB
- รถ: `Boom_ETL.vehicles.find({ active: true }, { projection: { code:1, plate_no:1, brand:1, plant:1 } })` ≈ 800 แถว ≈ 50 KB
- ยิงพร้อมกันด้วย `Promise.all` · **ห้ามเขียนลง `Boom_ETL` เด็ดขาด**

## ตัดทิ้งโดยตั้งใจ — อย่าเติมกลับเองถ้าไม่ได้สั่ง

- **ปุ่มลบคำขอ** (ยกเลิกแทน)
- **สถานะ “กำลังสัมภาษณ์” บนคำขอ** (ซ้ำกับใบสมัคร)
- **ช่อง `trucknum`/`plate`/`brand` แยกสามช่อง** ของฟอร์มเก่า (เลือกรถทีเดียวเติมครบ)
- **ป้าย “รถพร้อม/ไม่พร้อมใช้”** — `sub_status_nickname` ของระบบเก่ามาจาก FastAPI
  `/staticmixer/vehicles/autocomplete` **ไม่มีใน `Boom_ETL.vehicles`** (ตรวจแล้ว 21 ก.ย. 2026)
  สเปกนี้ไม่พึ่งมันเลยสักจุด
- **ผู้สมัครหลายคนต่อคำขอ**
- **หน้ารายละเอียดแยก** (แผง `⋯` พอ — สุดท้ายก็ไม่ได้สร้างแผงนี้เลย เพราะตารางเปลี่ยน
  เป็นอ่านอย่างเดียวทั้งใบไปก่อน)
- **โมดัลดินสอ/แผงแก้ไขรวมทุกช่องในตารางคำขอ** — ลองมาแล้วตั้งแต่เช้า (22 ก.ย. 2026)
  แล้วถูกถอดตามคำขอเจ้าของงาน ตารางกลับไปอ่านอย่างเดียวเป็นค่าเริ่มต้น **ยกเว้น
  ครูฝึกที่ขอกลับมาแก้ในช่องได้ตรง ๆ อีกครั้ง** (`TrainerCell` — ดูหัวข้อ “คอลัมน์
  ‘จัดการ’” สำหรับไทม์ไลน์เต็มสามรอบ) **ทะเบียนรถยังคงแก้ที่หน้าติดตามฝึกงานเหมือนเดิม**
  (ดูหัวข้อ “ทะเบียนรถไหลไปหน้าฝึกงานยังไง”) — **ผู้สมัครที่ผูก/รหัส พจส./หมายเหตุ
  ยังไม่มีจุดแก้ไขเหลืออยู่เลยในระบบตอนนี้** ถ้าจะเพิ่มจุดแก้ไขให้ช่องพวกนี้ **ต้อง
  ถามก่อนว่าจะแก้จากหน้าไหน** อย่าเดาเอาเอง — ประวัติที่ไปๆ มาๆ สามรอบของครูฝึก
  คือตัวอย่างว่าทำไมถึงต้องถาม
- **ช่องแก้/ผูกทะเบียนรถและครูฝึกตอนสร้างคำขอให้บังคับกรอก** — ตั้งใจเป็น `optional`
  เสมอ เพราะตอนแจ้งขอสรรหายังไม่รู้ว่าจะได้รถคันไหน/ใครเป็นครูฝึก กรอกได้ก็ต่อเมื่อ
  รู้แล้วเท่านั้น (ปกติคือตอนคนนั้นเริ่มฝึกงาน) — **ห้ามบังคับ** ไม่ว่าจะแก้จากฟอร์ม
  สร้างหรือจากหน้าติดตามฝึกงาน
