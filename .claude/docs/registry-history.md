## ภาพรวม

`mena-next-lb` มีหน้า `/registry-history` อยู่แล้ว แต่ **ไม่ได้ต่อ MongoDB ตรง** — ทุก route ใน
`src/app/api/registry-history/**` เป็นแค่ proxy ไปยัง service ภายนอก (env `MONGODBAPI`,
ดู `mongodb-api.ts` ของโปรเจกต์นั้น) ซึ่ง source ของ service นั้นไม่ได้อยู่ใน repo ไหนที่เข้าถึงได้ตอนนี้

สิ่งที่ยืนยันแล้วคือ**ต้นทางข้อมูลจริง** อยู่ที่ MongoDB Atlas คลัสเตอร์เดียวกับที่ `hr-service`
ต่ออยู่ (`MONGO_URI` ใน `.env.local`) — database ชื่อ **`Boom_ETL`** (ไม่ใช่ db ที่ `getDb()`
ของ `lib/mongo.ts` ชี้ไปตามปกติ ซึ่ง default เป็น `hr_service` — ต้อง `client.db("Boom_ETL")` เอง
ถ้าจะอ่านชุดนี้ อย่าไปแก้ `MONGO_DB` ของทั้งระบบเป็น `Boom_ETL` เพราะ `record_cases` ฯลฯ อยู่คนละ db)

```
Boom_ETL (Atlas, คลัสเตอร์เดียวกับ hr_service)
  ├─ main_driver              ← ทะเบียนคนขับ (ETL sync)
  ├─ employee_work_status     ← สถานะการทำงานรายเดือน (ETL sync)
  └─ vehicles                 ← ทะเบียนรถ (ETL sync, join กับ main_driver.vehicle)
```

**⚠️ ฟิลด์ที่ `mena-next-lb` โชว์ในหน้าเว็บแต่ "ไม่มี" ในเอกสารดิบนี้เลย:**
`resign_notice_date` `resign_date` `resign_recorded_at` `resign_recorded_by` `resign_reason*`
`photos` `resign_photos` `work_status` `work_status_date` `vehicle_info` (fleet/plant/vehicle_type)

แปลว่า service `MONGODBAPI` ที่ mena-next-lb เรียกอยู่ **ไม่ได้อ่าน `Boom_ETL.main_driver` ตรงๆ
แล้วส่งออกทั้งดุ้น** — มันต้อง enrich เพิ่มอย่างน้อย 2 ทาง:

1. **join กับ `vehicles`** (เอา `fleet`/`plant`/`vehicle_type` มาแปะเป็น `vehicle_info`)
2. **join กับ `employee_work_status`** (เอา `latest_status`/`latest_work_date` มาแปะเป็น `work_status`/`work_status_date`)
3. **overlay ข้อมูลลาออก/รูปถ่าย** ที่เขียนผ่าน `PATCH /main-driver/{id}/resign` และ `/photos` —
   ฟิลด์พวกนี้ไม่มีใน `_source`/ETL เลย จึงต้อง**เก็บแยกอีกที่หนึ่ง** (คนละ collection/คนละ db
   จาก `Boom_ETL` ที่เป็น mirror อย่างเดียว) — **ยังไม่พบว่าเก็บที่ไหน**, ต้องหา service
   `MONGODBAPI` ตัวจริงถึงจะรู้ ถ้าเขียนทับ `main_driver` ตรงๆ ข้อมูล resign จะหายทุกรอบที่ ETL sync ใหม่

**ข้อควรระวังถ้าจะทำ read-only ทะเบียนประวัติจาก `Boom_ETL` ตรงๆ:** จะได้แค่ข้อมูลพื้นฐาน
(ชื่อ, รหัส, สังกัด, วันเริ่มงาน, เบอร์โทร, สถานะ active) — **ไม่มีประวัติลาออก/รูป/สถานะทำงานละเอียด**
ต้อง join เพิ่มเองหรือยอมรับว่าไม่มี

## สีของ `ลอ` / `ปอ` — พ้นสภาพเป็นแดงทุกที่ (21 ก.ย. 2026)

`ลอ` (พจส.ลาออก) กับ `ปอ` (พจส.ถูกปลด) **ไม่ใช่ “วันที่ไม่ได้ทำงาน”** เหมือน `ล`
หรือ `X` แต่เป็นวันสุดท้ายของการเป็นพนักงาน · ทั้งระบบใช้ `alert` (แดง) กับการ
พ้นสภาพอยู่แล้ว (วงรูปใน `DriverAvatar` · ป้ายใน `DriverStatusControl`) สองรหัสนี้
จึงถูกแยกเป็นโทน **`exit`** ให้สีตรงกัน

| ที่ | ไฟล์ | คลาส |
|---|---|---|
| เกณฑ์กลาง | `_lib/drivers/types.ts` → `EXIT_STATUS_CODES` · `isExitStatus()` · `workStatusTone()` | — |
| ชิปสถานะล่าสุด (ตารางทะเบียน) | `driver-registry-view.tsx` → `WORK_TONE` | `bg-alert-soft text-alert` |
| ปฏิทินทั้งปีรายคน | `driver-work-year.tsx` → `TONE_BG` `TONE_BAR` `TONE_LABEL` | `bg-alert text-ink-content` |
| ตารางติดตามฝึกงาน | `_lib/drivers/trainees.ts` → `TONE_FILL` `TONE_TEXT` `TONE_DOT` | `var(--color-alert)` |

⚠️ **ลำดับการตรวจในทั้ง `workStatusTone()` และ `cellTone()` สำคัญ** — `ลอ` ขึ้นต้น
ด้วย “ล” จึงเข้าเงื่อนไข `/^[ลL]/` ของกองลาด้วย · ถ้าย้าย `isExitStatus()` ลงไป
ทีหลัง วันที่คนลาออกจะกลับไปเป็นสีเหลืองเหมือนวันลาธรรมดาเงียบ ๆ
(เหตุผลเดียวกับที่ `resolveOwnerTypeKey()` ต้องเช็ก “สแปร์” ก่อน “พจส”)

`ink-content` พลิกเป็นสีเข้มในธีมมืด ซึ่งพอดีกับ `alert` ที่สว่างขึ้น (#ff7a70)
— คู่นี้จึงคอนทราสต์ผ่านทั้งสองธีมโดยไม่ต้องเขียนเงื่อนไขแยก

## คนที่พ้นสภาพบนหน้าติดตามฝึกงาน (21 ก.ย. 2026)

**เห็นเฉพาะคนที่พ้นสภาพ “ในเดือนที่เปิดอยู่” เท่านั้น** — เดือนที่คนคนหนึ่งออกคือ
เดือนที่ยังต้องเห็นเขา (คนที่ฝึกอยู่แล้วหายไปกลางคันคือข้อมูลที่ฝ่ายบุคคลต้องใช้)
ส่วนเดือนถัดไปไม่ต้องมีเขาอีก · แถวของคนกลุ่มนี้ขึ้น **ธีมแดงทั้งคอลัมน์พนักงาน**
(พื้น `alert-soft` · `Avatar tone="alert"` · ชื่อเป็น `text-alert` · บรรทัดอายุงาน
ถูกแทนด้วย “พ้นสภาพ ‹วันที่›”) ไม่ใช่แค่ป้ายเล็ก ๆ เพราะคนอ่านกวาดตาดูคอลัมน์ซ้าย
ทีละสิบแถว ป้ายบรรทัดที่สามถูกมองข้ามได้ง่าย

**สัญญาณที่ใช้ตัดสิน เรียงตามความน่าเชื่อ** (`getTraineeBoard()`):

1. `master_driver.resignation.dateISO` — วันที่ฝ่ายบุคคลบันทึกเอง แม่นที่สุด
2. รหัส `ลอ`/`ปอ` ในสถานะรายวันของเดือนนั้น (ATMS หรือที่กรอกเอง) เอาวันหลังสุด
3. `employee_work_status.latest_status` เป็น `ลอ`/`ปอ` → ใช้ `latest_work_date`
4. `statusOverride: "resigned"` หรือ `active: false` — บอกแค่ว่าออกแล้ว ไม่บอกว่าเมื่อไหร่

**ไม่รู้วันที่ = ถือว่าไม่ได้พ้นในเดือนนี้ → ซ่อน** ดีกว่าเดาแล้วให้คนที่ออกไปตั้งแต่
ปีที่แล้วโผล่ค้างอยู่ · ข้อ 3 สำคัญกว่าที่คิด: วัดกับข้อมูลจริงพบ **17 คนที่ ETL
ยังตั้ง `active: true` ทั้งที่ `latest_status` เป็น `ลอ`/`ปอ` ไปแล้ว** — ถ้าดูแค่
`active` คนกลุ่มนี้จะค้างอยู่ในตารางตลอดไป · `latest_status` / `latest_work_date`
เป็นฟิลด์บนสุดสองช่อง ขอมาใน projection เดียวกับเดือนที่เปิดอยู่ **แทบไม่มีต้นทุน**
— ห้ามไปอ่าน `months` ทั้งก้อนเพื่อหาคำตอบนี้ นั่นคือ 3.5 MB ที่ตัดทิ้งไปแล้ว

query ของ `master_driver` เป็น `$or` สามทาง: `active: true` · `statusOverride: "active"`
(ฝ่ายบุคคลยืนยันว่ายังทำงาน ทับค่า ETL) · `resignation.dateISO` อยู่ในเดือนนั้น
— ยังเป็น COLLSCAN เหมือนเดิม (~150 ms / 2,617 แถว) เพราะไม่มี index บน `active`
และ selectivity ต่ำเกินกว่าจะคุ้มสร้าง
