# เงื่อนไขเปลี่ยนตอนไหน ต้องทำอะไร

> คู่มือสำหรับ "วันหนึ่งข้างหน้าเงื่อนไขไม่เหมือนเดิม" · ปรับปรุง 14 ต.ค. 2569

ระบบนี้มีเงื่อนไขอยู่สองชั้น และ **สองชั้นนี้เปลี่ยนคนละวิธี โดยตั้งใจ**

| | เปลี่ยนบ่อย | ใครเปลี่ยน | เปลี่ยนที่ไหน | ต้อง deploy ไหม |
|---|---|---|---|---|
| **สถานะการทำงาน** | ทุกเดือน | HR กดเอง | หน้าจอ | **ไม่ต้อง** |
| **สัญญาเรื่องข้อมูล** | นาน ๆ ครั้ง | ผ่านการรีวิวโค้ด | ไฟล์ในรีโป | ต้อง |

เหตุผลที่ไม่ยกทุกอย่างขึ้นหน้าจอ: การเปลี่ยน "ช่องนี้เป็นเงินหักนะ" คือการเปลี่ยนเงินในสลิป
ของพนักงานทุกคน ควรมีคนที่สองดูก่อนเสมอ ส่วน "เดือนนี้เปิดรอบแล้ว" ไม่ควรต้องรอโปรแกรมเมอร์

---

## ชั้นที่ 1 — กดเองได้ ไม่ต้อง deploy

### เปิด/ปิดรอบจ่าย
หน้า `/payroll/intake` → เลือกเดือน → ปุ่ม **เปิดรอบนี้** / **ปิดรอบนี้** (เห็นเฉพาะค่าจ้างและสวัสดิการ)

- รอบที่ยังไม่เปิด = ฝ่ายอัปโหลดไม่ได้ และยิง API ตรงก็ไม่ได้
- ปิดรอบแล้วยังเปิดดูย้อนหลังได้ แต่เขียนอะไรไม่ได้อีก · เปิดกลับได้ถ้าเจอว่าฝ่ายส่งผิดไฟล์
- ระบบบันทึกว่าใครเปิด/ปิดเมื่อไหร่ (คอลเลกชัน `payroll_periods`)

### ผู้รับอีเมลแจ้งฝ่าย
กล่อง **ร่างอีเมลแจ้งฝ่าย** → แก้ช่อง ถึง/สำเนา → **บันทึกไว้ใช้รอบหน้า**
(ค่าเริ่มต้นมาจากสมุดรายชื่อ NCAC · กดกลับไปใช้สมุดรายชื่อได้ตลอด)

### ใครตรวจรับเข้ารอบได้
ตัวแปรระบบ `NEXT_PUBLIC_PAYROLL_APPROVER_DEPARTMENTS` (ค่าเริ่มต้น = ค่าจ้างและสวัสดิการเท่านั้น)
— แก้ที่ค่าตั้งของระบบ ไม่ต้องแก้โค้ด แต่ต้อง restart

## ชั้นที่ 2 — ต้องแก้ในรีโปและผ่านการรีวิว

**ทุกการเปลี่ยนในชั้นนี้ลงท้ายเหมือนกัน:**

```bash
npm run verify:payroll      # ตรวจว่าเงื่อนไขยังสอดคล้องกันทั้งระบบ
npm test                    # 166 ข้อ รวมด่านกันเปลี่ยนเงื่อนไขเงียบ ๆ
npm run snapshot:payroll    # อัปเดตภาพรวมเงื่อนไข แล้ว commit ไปด้วย
```

`lib/payroll/contract.snapshot.txt` คือภาพรวมเงื่อนไขทั้งหมดในไฟล์เดียว —
แก้อะไรก็ตามในชั้นนี้แล้ว **เทสต์จะล้มพร้อมบอกบรรทัดที่เปลี่ยน** ต้องตั้งใจอัปเดต snapshot
ถึงจะผ่าน · ทำให้ diff ของ PR แสดงผลกระทบจริง ไม่ใช่แค่ "แก้โค้ด 1 บรรทัด"

### ได้คำตอบความหมายรหัสวัน (เหลือ 9 รหัส)
`DAY_CODES` ใน `lib/payroll/template-spec.ts` → เติม `meaning` + `evidence` (ใครบอก เมื่อไหร่)
ผลทันที: กฎเปลี่ยนจาก "รอยืนยัน" เป็นใช้งานได้เอง ไม่ต้องแก้ที่อื่น

### ได้คำตอบทิศทางเงิน (#14 เบิกสำรอง · #17 ค่าปะ-เปลี่ยนยาง)
`MONEY_COLUMNS` ใน `lib/payroll/classify.ts` → เปลี่ยน `"รอยืนยัน"` เป็น `"เพิ่ม"` หรือ `"หัก"`
แล้วลบรายการนั้นออกจาก `WAITING_OWNER` ใน `rules.ts`
ผลทันที: ด่านแรกเริ่มตรวจเครื่องหมายบวกลบให้ · **เดาไม่ได้เด็ดขาด เดาผิดคือจ่ายแทนที่จะหัก**

### ลูกค้า/ศูนย์/กลุ่มใหม่ในฟอร์มรวม
`MERGE_COLUMN` ใน `lib/payroll/registry.ts` → เพิ่มค่าใน `values`
ไม่เพิ่มแล้วฝ่ายกรอกเข้ามา = ด่านแรกบล็อกทั้งไฟล์ (ตั้งใจ — กันแถวที่ไม่รู้ว่าเป็นของใคร)

### ฝ่ายส่งฟอร์มที่คอลัมน์เปลี่ยน
1. `TEMPLATE_SPECS` ใน `template-spec.ts` → แก้ `columns` (**ชื่อคอลัมน์คือสัญญากับฝ่ายที่ส่ง
   ห้ามเปลี่ยนโดยไม่คุยกับเขาก่อน** — ไฟล์ที่เขากรอกค้างไว้จะพังทันที)
2. ถ้าเป็นช่องตัวเลข → เพิ่มใน `MONEY_COLUMNS` ด้วย ไม่งั้น `verify:payroll` ไม่ผ่าน
3. ถ้าเป็นช่องข้อมูล → เพิ่มใน `DIMENSION_OF` (`normalize.ts`) ไม่งั้น `verify:payroll` ไม่ผ่าน

ข้อ 2–3 **บังคับโดยเครื่อง ไม่ใช่โดยความจำ** — ช่องที่ไม่ได้ขึ้นทะเบียนคือข้อมูลที่จะหาย
เงียบ ๆ ตอนรวมตาราง ระบบจึงไม่ยอมให้ผ่านตั้งแต่ตอนตรวจ

### เพิ่มรายการใหม่ในทะเบียน
`INTAKE_ITEMS` (`registry.ts`) + `TEMPLATE_SPECS` + `MONEY_COLUMNS`
— **เลขรายการห้ามใช้ซ้ำกับของเดิมหรือของที่ปลดระวางแล้ว** เพราะเลขเป็นคีย์สถานะรายรอบ
(`payroll_intake._id = "<รอบ>:<รายการ>"`) ใช้ซ้ำแล้วประวัติจะปนกัน

### รวมหรือเลิกใช้รายการ
ย้ายเข้า `RETIRED_ITEMS` (`registry.ts`) พร้อมบอกว่ารวมเข้าเลขไหน ตั้งแต่รอบไหน
— อย่าลบทิ้งเฉย ๆ รอบเก่าที่ส่งไปแล้วยังอ้างเลขนั้นอยู่

### ได้สเปกไฟล์นำเข้า Tiger Soft
เขียนตัวแปลงจาก `sumByPayee()` ใน `lib/payroll/normalize.ts` (ยอดรวมต่อคน แยกเพิ่ม/หัก พร้อมแล้ว)
— ส่วนที่ยังไม่รู้คือรูปแบบไฟล์ปลายทาง ไม่ใช่ตัวเลข

ดู [`payroll-intake-open-questions.md`](./payroll-intake-open-questions.md) — ตารางบอกว่า

## เรื่องที่ตั้งใจยังไม่ทำ

- **ยกทะเบียน/ผังคอลัมน์ขึ้นหน้าจอให้ HR แก้เอง** — เป็นไปได้ แต่การแก้ผิดหนึ่งช่องเปลี่ยนเงินในสลิป
  ทุกคน ควรผ่านการรีวิวก่อน ถ้าวันหนึ่งความถี่การแก้สูงจนเป็นภาระจริง ค่อยทำหน้าจอพร้อมขั้นอนุมัติสองชั้น
  แบบเดียวกับด่าน 2
- **คิดวันทำงานจากรหัสวันอัตโนมัติ** — ทำได้เมื่อรหัสที่เหลือ 9 ตัวได้คำตอบครบ
