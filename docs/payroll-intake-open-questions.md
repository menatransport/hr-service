# ระบบรับข้อมูลเงินเดือน: เรื่องที่ยังรอคำตอบ

เอกสารนี้บอกว่า**ส่วนไหนของระบบตั้งใจทำไม่ครบ เพราะอะไร และต้องรอใคร** เขียนให้คนที่ไม่เคยอยู่ในวงคุยอ่านเข้าใจได้เอง

## อ่านก่อน: ทำไมถึงไม่เดา

ระบบนี้รับไฟล์จาก 6 ฝ่ายเพื่อรวมเป็นข้อมูลเงินเดือน ด้านที่ระบบตัดสินเองไม่ได้ เรา**ไม่เดา** เพราะทั้งสองทางเสียหายเหมือนกัน

- เดาแล้วบล็อก: เงินเดือนหยุดค้างด้วยกติกาที่เราแต่งขึ้นเอง
- เดาแล้วปล่อย: จ่ายผิดโดยไม่มีใครรู้

กฎที่ตัดสินไม่ได้จึงมีสถานะ **รอยืนยัน (pending)** ซึ่งขึ้นบนจอให้คนเห็นว่ากำลังรอเรื่องอะไร แต่**ไม่บล็อกใคร** ส่วนเรื่องที่ไม่ใช่การตรวจ (เช่น ไฟล์นำเข้า Tiger Soft) ยังไม่ได้สร้างเลย เพราะยังไม่รู้รูปแบบที่ต้องส่ง

ดูว่าแต่ละรายการมีกฎตรวจจริงกี่ข้อ รอยืนยันกี่ข้อ และรอใคร ได้ด้วย `npm run verify:payroll` (ส่วน "กฎต่อรายการ" ท้ายผลลัพธ์)

## รายละเอียดแต่ละเรื่อง

### 1. รหัสวัน 17 จาก 24 ตัว

ตารางสถานะรายวันใช้รหัสทั้งหมด 24 ตัว ที่ยังไม่รู้ความหมายคือช่อง `meaning` ที่ยังว่างใน `DAY_CODES` ไม่รู้ว่าวันที่ลงรหัสนั้นนับเป็นวันทำงานและได้เงินหรือไม่ ระบบจึงยังคิดวันทำงานจากไฟล์ #01 ไม่ได้

- รหัสที่ไม่อยู่ใน 24 ตัวเลย = ผิดแน่ บล็อกได้ (`daycode.unknown`)
- รหัสที่อยู่ในชุดแต่ยังไม่รู้ความหมาย = ขึ้นเตือน ไม่บล็อก (`daycode.meaning-pending`)
- ระวังอย่าเอารหัสของเครื่องลงเวลา TA100 มาปน `A` ของสองชุดแปลไม่เหมือนกัน

รหัสที่ `meaning` ยังว่าง 17 ตัว: Aส Aป Aน Aด Aค Aซ Aล AX ลส กด กม ย จ ลซ ลข ลพ ก

**7 ตัวมีเบาะแสจากไฟล์ของฝ่ายจัดส่งเอง — ถามแค่ว่า "ใช่ไหม" พอ**

ชีต `ค่าวินัย-โม่ใหญ่` / `ค่าวินัย-โม่เล็ก` ในไฟล์ `4. สถานะทำเงินเดือนพจส.และสถานะวันทำงานพจร.xlsx`
มีคอลัมน์สรุปที่นับรหัสด้วย `COUNTIF` แล้วตั้งชื่อหัวคอลัมน์ไว้ตรง ๆ:

| รหัส | หัวคอลัมน์ที่นับรหัสนี้ | น่าจะแปลว่า |
|---|---|---|
| `Aส` | สรุป สาย | มาทำงาน แต่สาย |
| `Aป` | สรุปไม่โอน | มาทำงาน แต่ไม่โอน |
| `Aน` | สรุป หนี | มาทำงาน แต่หนีงาน |
| `Aด` | สรุป ด่า | มาทำงาน แต่มีเรื่องด่า |
| `ก` | สรุปกิจฉุกเฉิน | ลากิจฉุกเฉิน |
| `ป` | สรุปป่วย ฉุกเฉิน | ป่วยฉุกเฉิน (ยืนยันแล้วว่า "ป่วย" — ขอความชัดว่าเป็นแบบฉุกเฉินหรือไม่) |
| `ลซ` `ลข` `ลพ` | นับแยกคนละคอลัมน์ | ลาชนิดที่ทำให้เสียค่าวินัย (ยังไม่รู้ว่าแต่ละตัวคืออะไร) |

สูตรจ่ายค่าวินัยในไฟล์เดียวกันบอกเพิ่มว่า: ได้ค่าวินัย (โม่ใหญ่ 500 · โม่เล็ก 300) เมื่อ
สาย ≤ 1 วัน · กิจฉุกเฉิน ≤ 1 วัน · วันทำงาน ≥ 27 วัน · และ `Aป` `Aน` `Aด` `ลข` `ลพ` `ลซ`
เป็นศูนย์ทุกตัว — หกรหัสนี้จึงเป็นรหัส "มีความผิด" ไม่ใช่รหัสกลาง ๆ

**เบาะแสยังไม่ใช่คำยืนยัน** — ระบบยังนับทั้ง 17 ตัวเป็น "รอยืนยัน" เหมือนเดิม ไม่เอาไปคิดเงิน
(`candidate` ใน `DAY_CODES` แยกจาก `meaning` คนละช่อง) หน้าจอกับแบบฟอร์มแสดงเบาะแสพร้อมที่มา
เพื่อให้ฝ่ายจัดส่งทักท้วงได้ทันทีถ้าผิด

ยังไม่มีเบาะแสเลย 8 ตัว: `Aค` `Aซ` `Aล` `AX` `ลส` `กด` `กม` `ย` `จ`

เมื่อได้คำตอบ: เติม `meaning` ของแต่ละรหัสใน `DAY_CODES` แล้วกฎจะเปลี่ยนจากรอยืนยันเป็นใช้งานเอง

### 2–3. ทิศทางเงินที่ยังไม่ยืนยัน

รายการ #14 เบิกสำรอง (รอบัญชีกรุงเทพ) และ #17 ค่าปะ-เปลี่ยนยาง (รอยานยนต์) มีช่องเงินที่อ่านจากชื่อช่องแล้วตัดสินไม่ได้ว่าเป็นเงินเพิ่มหรือเงินหัก จึงจัดเป็น `รอยืนยัน` ไม่เดา เพราะเดาผิดคือจ่ายแทนที่จะหัก ระบบตรวจเครื่องหมายบวกลบของสองรายการนี้ไม่ได้ ต้องให้คนดูยอดเองก่อนรับเข้ารอบ

(เดิมเป็นสี่รายการ #14 #15 #17 #18 — รวมฟอร์มแล้วเหลือสอง คำถามเท่าเดิม)

เมื่อได้คำตอบ: เปลี่ยน `"รอยืนยัน"` เป็น `"เพิ่ม"` หรือ `"หัก"` ในแถวของรายการนั้นใน `MONEY_COLUMNS` และลบรายการนั้นออกจาก `WAITING_OWNER` ใน `lib/payroll/rules.ts` (สคริปต์ตรวจจะแจ้งถ้าสองที่นี้ไม่ตรงกัน)

### 4–5. Tiger Soft

- **#08 เงินรางวัล** มี 4 ช่องย่อย และ **#23 ค่าหัก** มีค่าน้ำกับค่าไฟแยกกันสองช่อง ตอนนี้ลงช่องรวมและถือช่องย่อยเป็นข้อมูลอ้างอิง เพราะ 1 รายการในทะเบียน = 1 รหัสรายได้หรือรายหัก ลงทั้งรวมทั้งย่อยคือลงซ้ำ แต่ถ้า Tiger Soft ต้องการแยกรหัสตามช่องย่อย ต้องสลับ
- ยังไม่รู้สเปกไฟล์นำเข้าของ Tiger Soft ระบบจึงจบที่หน้าสรุป (และ Excel สรุปที่ระบุชัดว่าไม่ใช่ไฟล์นำเข้า) ยังไม่ได้สร้างไฟล์นำเข้า

กฎที่เกี่ยวข้องเป็นระดับ `info` สถานะ pending ไม่กระทบการรับเข้ารอบ กระทบเฉพาะตอนทำไฟล์นำเข้าในอนาคต

### 6. รหัสหน่วยงาน

รหัสนี้ตัดสินว่าใครเห็นและอัปโหลดไฟล์ของใครได้ จึงใส่เลขที่เดาเอาไม่ได้ (เดาผิดคือเปิดให้ฝ่ายหนึ่งส่งแทนอีกฝ่ายโดยไม่มีใครรู้) ยืนยันแล้ว 4 ฝ่าย: ยานยนต์ (3), Operation Support (11), จัดส่ง ลาดกระบัง (15), HR C&B (24) ที่เหลือสองฝ่ายเป็น `null`

ระหว่างรอ: ผู้ดูแลระบบใส่ชั่วคราวได้ด้วยตัวแปร `NEXT_PUBLIC_PAYROLL_OWNER_DEPARTMENTS` เมื่อได้รหัสจริงให้ย้ายมาใส่ในตารางตรง ๆ แล้วลบตัวแปรนั้นออก

### 7. แบบฟอร์มร่าง

#06 #24 ยังไม่เคยได้ไฟล์จริงจากฝ่ายเจ้าของข้อมูล โครงคอลัมน์ในระบบจึงเป็นร่าง (`confirmed: false`) ระบบเทียบคอลัมน์แบบบังคับไม่ได้ กฎ "ขาดคอลัมน์" ของรายการเหล่านี้จึงเป็น pending

เมื่อได้ไฟล์จริง: แก้ `columns` และ `source` ของรายการนั้นใน `TEMPLATE_SPECS` แล้วเปลี่ยนเป็น `confirmed: true` จากนั้นรัน `npm run verify:payroll` เพราะสเปก การจัดประเภทเงิน และกฎ อ้างถึงกันด้วยชื่อช่องเป็นข้อความ

## เมื่อได้คำตอบแล้ว

1. แก้ที่ตามคอลัมน์ "แก้ที่" ด้านบน
2. รัน `npm test && npm run verify:payroll && npm run lint`
3. ดูส่วน "กฎต่อรายการ" ของ `verify:payroll` ว่าจำนวน "รอยืนยัน" ของรายการนั้นลดลงตามคาด
